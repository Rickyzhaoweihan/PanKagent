# Isolated PanKgraph 0919 query API

`pankgraph0919_backend` is a standalone FastAPI application for the dedicated
`pankgraph0919` Neo4j and PostgreSQL databases. It does not import the legacy
agent, results backend, their authentication modules, or deployment helpers.
The repository's other applications and ports 8794, 8795, and 8796 are outside
this service's ownership.

The external `context-aware-kg-standard` package supplies `cakg.identity` and
`cakg.multimodal`, using the `cakg_mm` schema. Install its pinned release before
starting this app; the dependency pin belongs in `requirements-0919.txt` and
the deployment release manifest. The pinned upstream revision is
`63c0b62bb5d7810ccf918affbe1c9dff11c0bafe` from
[context-aware-kg-standard](https://github.com/RingoMao/context-aware-kg-standard).
The separately verified wheel SHA-256 is
`3703f9086dcc8db30d22516c597f0e5780c8e2f57b03cb0b25a7d850fa382629`.
Python 3.12 or newer is required by the
standard. This service never creates schemas, imports evidence, or accepts SQL
from clients.

## Private configuration and launch

All configuration comes from the `PANK0919_` namespace. Never put values of
passwords, DSNs, or API tokens into this documentation, Git, command arguments,
or shared acceptance output.

| Environment variable | Requirement or default |
| --- | --- |
| `PANK0919_NEO4J_URI` | Credential-free loopback Bolt URL with explicit port; deployment uses `bolt://127.0.0.1:17919` |
| `PANK0919_NEO4J_USER` | Dedicated isolated Neo4j account |
| `PANK0919_NEO4J_PASSWORD` | Required private credential |
| `PANK0919_NEO4J_DATABASE` | Exactly `pankgraph0919` |
| `PANK0919_POSTGRES_READ_DSN` | Explicit loopback host and port, `dbname=pankgraph0919`, `user=pankgraph0919_reader`; deployment uses port 15919 |
| `PANK0919_POSTGRES_READ_USER` | Exactly `pankgraph0919_reader` |
| `PANK0919_API_TOKEN` | Required bearer token, at least 32 characters |
| `PANK0919_SNAPSHOT_ID` | One immutable accepted release identifier |
| `PANK0919_PORT` | 18919; app server invocation must use the same owned port |
| `PANK0919_QUERY_TIMEOUT` | 10 seconds, allowed 1–30, per database statement |
| `PANK0919_MAX_ROWS` | 200, allowed 1–200 |
| `PANK0919_MAX_BYTES` | 2,000,000 UTF-8 bytes, allowed 1,024–2,000,000 |
| `PANK0919_ALLOW_SENSITIVE_RECORDS` | `false`; only explicit `true` enables sensitive or unclassified SQL detail fields |

The PostgreSQL reader must have SELECT-only grants on `cakg_mm`, no ownership
or mutation grants, and no privileged role memberships. The Neo4j instance must
be dedicated and configured read-only after accepted import; routing with
`READ_ACCESS` alone is not a write permission boundary. Both services bind to
loopback. A deployment manager, independently owned by this release, should run
the app with its private environment loaded:

```sh
python -m uvicorn pankgraph0919_backend.app:create_app --factory --host 127.0.0.1 --port 18919
```

The service disables automatic documentation/OpenAPI endpoints. It does not
configure public routing or CORS. An authenticated client must send
`Authorization: Bearer <private token>` on every data route.

## Acceptance and health

Startup checks the actual PostgreSQL database/user/read-only transaction state,
requires exactly one snapshot with the configured ID and `status='accepted'`,
and counts its registered nodes and edges. Neo4j must report the configured
database name; all actual graph nodes and relationships must carry that same
snapshot ID, and their counts must agree with PostgreSQL. The standard's import
gate performs exact canonical identity, label, relationship type, and endpoint
reconciliation before marking the release accepted.

A failed gate leaves a sanitized health endpoint available. Graph routes are
disabled until graph acceptance succeeds. PostgreSQL search, records, contexts,
and sources have an independent gate and work when Neo4j is unavailable but
PostgreSQL acceptance succeeds. Every SQL request checks acceptance again in its
read-only transaction. Graph brief requests use the accepted immutable snapshot
cache and perform no PostgreSQL operation. After a later SQL outage, previously
accepted graph reads can continue while PostgreSQL routes report unavailable.

`GET /health` needs no token and returns only `{"status":"ready"}` or
`{"status":"unavailable"}`. It refreshes both component checks after a
15-second cache lifetime, returning 200 only when both components pass, and 503
otherwise. `GET /health?detail=true` requires the bearer token and always refreshes
the checks, adding sanitized database identities, snapshot, and object counts.
It never includes addresses, credentials, driver errors, or query contents.

This is an immutable single-snapshot service. Replacing a release, changing
acceptance status, or changing accepted graph objects behind a running process
is unsupported. Stop the owned API, validate the replacement, and restart to
establish a new acceptance cache. The health cache is not a substitute for the
standard's exact import reconciliation.

## Routes and response contract

All data responses include `snapshot_id`. Paginated SQL results include `items`,
`total`, `limit`, `offset`, `has_more`, and `next_offset`, ordered by stable
canonical IDs. Offset is bounded at 1,000,000. Context and record filters are
exact matches; they do not perform ontology expansion or infer missing context.

| Route | Request and behavior |
| --- | --- |
| `POST /query` | Exactly one of `cypher` or `postgres_search`; optional `mode` is `brief` (default) or `detail` |
| `POST /genes/search` | Structured text or indexed genomic interval search in PostgreSQL; independent of Neo4j availability |
| `POST /records/search` | Structured search requiring at least one `collection_id`, `source_file_id`, or `context_id`; reaches records without graph objects |
| `GET /contexts` | Paginated contexts with evidence in the configured snapshot; accepts collection/context/kind/condition/cell-type/status filters |
| `GET /objects/{object_id}/records` | Explicit registered `cakg:n:v1:sha256:...` or `cakg:e:v1:sha256:...` ID; optional filters and pagination |
| `GET /sources` | All source files in the one immutable snapshot, including catalog-only sources; source status, checksums, retained record counts, and rejection counts |

For a brief graph query:

```json
{"cypher":"MATCH (g:Gene)-[r]->(c:Cell_type) RETURN g,r,c","parameters":{},"mode":"brief","limit":25}
```

The result contains `graph_rows`, canonical `object_ids`, `graph_snapshot_ids`,
and `graph_truncated`. Actual driver nodes/relationships are serialized with
`kind`, `id`, `properties`, and node labels or relationship type. Actual paths
retain nodes and edges. Scalar values and projected maps are returned as values;
their `id` fields never authorize record expansion.

For detail mode, `filters` accepts `source_file_id`, `collection_id`, `context_id`,
`context_kind`, `condition`, `cell_type_id`, and `record_status`. Returned genuine
relationships take precedence over returned nodes, so a cell node does not
accidentally expand every gene's evidence. If no relationship was returned,
genuine nodes are used. An explicit object-record request can retrieve broader
node evidence deliberately. Expansion checks object membership in the accepted
SQL registry and follows only explicit `object_evidence` links. It does not infer
links from names, scalar IDs, aliases, or adjacent graph nodes.

`evidence` includes its own pagination, `unfiltered_total`, and `match_status`:
`matched`, `no_matching_records`, or `no_evidence`. Scalar-only detail queries
return `no_graph_objects` and make no SQL request. Graph row `limit` and evidence
page `limit` share the outer value; `offset` affects evidence only. Evidence
filters and outer offsets are rejected in brief mode.

Gene search accepts `query` text (canonical ID/name/alias substring), or a complete
region: `chromosome`, `start`, `end`, and `assembly`. Chromosomes are `1`–`22`,
`X`, `Y`, or `MT`. Intervals use zero-based half-open coordinates; the assembly
must be supplied explicitly. When text and region are both supplied they are
combined with AND. PostgreSQL `entity_interval` is authoritative for coordinates;
Neo4j intentionally omits coordinate fields. Example structured request:

```json
{"postgres_search":{"query":"example","limit":25,"offset":0},"mode":"brief"}
```

For independent records search, use a collection/source/context ID obtained from
the source or context routes. The request also accepts all record filters plus
`limit` and `offset`. `unfiltered_total` counts records in the selected source,
collection, or context before condition/cell-type/status filters. For object
expansion it counts all explicitly linked records before all additional filters.
These are source-record counts; they are never presented as donor or cell counts.

## Scientific status and privacy

Record `assertion_status` is exactly `source_reported`, `validated`, or
`quarantined`. Source `status` is exactly `released`, `revoked`, or `unverified`.
The API preserves these labels and reports raw measurements and normalized metrics
without inventing significance, positivity, causality, denominators, or unresolved
units. `HAS_*_RESULT_*` relationships identify source-table result membership;
their existence does not establish a positive biological association.

Quarantined rows remain accessible through independent records search and may
support staging node evidence. They cannot expand as relationship evidence.
Relationship expansion also rejects records from non-released sources. Empty
record pages and retained rejections do not mean a biological result is absent.
Catalog-only source rows have a nullable byte checksum and must remain visibly
unverified; a catalog metadata checksum is not substituted for source bytes.

By default, only sources explicitly classified by the adapter as `public_aggregate`
or `public_metadata` expose SQL metrics, raw records, and detailed metadata.
Sensitive and unclassified sources retain provenance/status and full page/count
information while their metrics/raw records/context metadata/source metadata are
redacted with `details_redacted=true`. Context metadata and source rejection details
use the same conservative boundary. Operators may explicitly enable
`PANK0919_ALLOW_SENSITIVE_RECORDS=true` for the authorized private deployment.
This does not change authentication or graph assertions. Do not expose this
service publicly or mix protected donor details into compact graph properties.

## Query boundaries and validation

Cypher is a restricted procedure-free read subset. The API masks string literals,
quoted identifiers, and comments when checking clauses, rejects mutation/admin
clauses, multi-statements, procedures, extension functions, and reserved internal
parameters, then requires Neo4j `EXPLAIN` to report read-only query type `r`.
The actual query runs in a `READ_ACCESS` session against the exact database, with
a statement timeout and an outer row cap. Single-statement input may use normal
parameters; request bodies are capped at 64,000 bytes and parameters at 32,000
bytes. Every complete response is subject to the configured byte cap. Oversized
responses return 413, so clients should narrow projections or page sizes.

PostgreSQL reads use fixed SQL templates and bound parameters, explicit read-only
transactions, a statement timeout, and a checked dedicated role. No raw SQL
endpoint exists. A request can run several bounded statements; the timeout is
per statement, not a single end-to-end HTTP deadline. Driver exceptions are
sanitized and logs record only exception class, never message/parameters/secrets.

Run the isolated acceptance tests without live drivers:

```sh
python -m pytest tests_0919/test_api.py -q
```

Tests cover auth, health cache refresh, accepted snapshot gates, driver read mode
and timeout, write/procedure rejection, scalar identity spoofing, returned-edge
priority, snapshot and endpoint mismatches, independent PostgreSQL paths,
pagination, source statuses, quarantine restrictions, source denominators,
privacy redaction, parameter binding, row/byte limits, and sanitized exceptions.
These tests do not prove live database acceptance or scientific correctness;
deployment acceptance must verify real authenticated routes and retained sources.
